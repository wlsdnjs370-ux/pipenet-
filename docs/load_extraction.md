# 유량 누적 기반 배관망 확정 — 알고리즘과 적용 한계

대상 코드: `remote30_prototype.py` 의 `compute_edge_load`, `prune_by_load`,
`select_worst30_heads_anchored(load_mode=...)`.
근거 지시서: `ModuleA_유량누적_작업지시서.md`. 미해결 모순은 `BLOCKED.md` §11·§12.

## 1. 표준 명칭

- **유량 누적(flow accumulation)** — 수문학/GIS 의 표준 절차. ① 흐름 방향 결정
  ② 상류 셀 누적 ③ 임계값 절단. D8 계열과 같은 구조다.
- **서브트리 단말 수(subtree terminal count)** — 루트 트리에서 각 간선 아래에 달린
  단말(=헤드) 수. 여기서는 헤드가 단말이다.
- **간선 매개중심성의 제한판** — 단일 소스 대 단말 집합으로 제한한 형태.
- 절단부는 **mark-and-sweep / dead code elimination** 과 같다. 다만 boolean 이 아니라
  **개수(counter)** 를 남기는 점이 다르고, 그 개수가 곧 담당 헤드 수다.

## 2. 왜 O(V+E) 인가

부모→자식 순서로 나열된 DFS 순서를 뒤집으면 후위순회가 된다. 후위순회에서 각 노드는
자식의 서브트리 합을 이미 알고 있으므로 **노드당 1회 방문, 간선당 1회 갱신**으로 끝난다.
따라서 O(V+E).

헤드마다 소스까지 거슬러 올라가는 방식(외부 PoC `water_cleanup`, 그리고 본 저장소의
`water_load_audit`)은 O(단말 수 × 깊이) 다. 결과는 같지만 복잡도가 다르며,
`water_load_audit` 은 그래프를 고치지 않는 **감사 전용**이라 그대로 둔다.

## 3. 전제 조건

1. **단일 급수원.** 부하는 하나의 소스를 루트로 한 하나의 최단경로 트리 위에서만
   정의된다. `src` 가 없으면 부하가 전부 0 이 되어 망 전체가 지워지므로,
   `load_mode` 는 이 경우 **자동으로 꺼지고** audit 의
   `fallback {triggered: true, reason: "source 미결합 — 부하 정의 불가"}` 에 기록된다.
2. **헤드 집합 확정이 선행.** 헤드 검출(S240 / W1 region 게이트)이 실패하면 모든 부하가
   0 이 되어 망 전체가 죽은 배관으로 판정된다. 부하는 헤드 검출의 하류 공정이지
   대체재가 아니다.
3. **가지식(트리) 우세.** 아래 4 참조.

## 4. 성립하지 않는 경우와 폴백

| 경우 | 왜 안 되는가 | 폴백 |
|---|---|---|
| 다중 급수원 | 루트가 둘 이상이면 "상류"가 정의되지 않는다. 어느 소스에서 오는 물인지에 따라 담당 헤드가 달라진다. | `load_mode` 를 켜지 않는다. 기존 `force_spanning_tree` 경로 유지. 소스 결합 실패 시에는 자동 폴백(위 3-1). |
| 완전 격자식 | 최단경로 트리는 사각 루프마다 반드시 변 하나를 비트리로 남기고 그 변의 부하는 정의상 0 이다 → 격자가 보존되지 않는다(`BLOCKED.md` §11). | `prune_by_load` 는 부하 dict 를 **인자로** 받으므로, 루프를 보존하는 다른 부하 정의(다중경로 유량 분배 등)를 넣으면 그대로 동작한다. 그 정의는 본 작업 범위 밖. |
| 환상 배관(ring main) | 위와 같은 이유. 환상 구간은 양방향 급수가 설계 의도인데 트리 부하는 한 방향만 센다. | 동일. 필요하면 `on_residual_cycle="force_tree"` 로 잔여 사이클을 명시적으로 끊고 그 사실을 audit `residual_cycles.policy` 로 남긴다. |
| 헤드가 상위 K(기본 30)를 넘는 도면 | S430 의 별표1 최소 호칭경은 **선정된 top-K** 만 세고, 파이프라인 부하는 **승인된 전체 헤드**를 센다. | 두 값을 통합하지 않는다(`BLOCKED.md` §12). 호칭경 산정은 S430 경로를 그대로 쓴다. |

## 5. 현행 `force_spanning_tree` 대비 무엇이 나아지나

`force_spanning_tree` 는 **위상만 보고** 자르므로, ① 실재하는 격자 배관을 파괴하고
② **죽은 배관을 못 없앤다** — 드레인·시험배관·막다른 가지는 "도달 가능"하므로 신장
트리에 그대로 살아남는다. "도달 가능"은 "물이 흐름"보다 넓다.

부하 기준 절단은 ②를 해결한다. 대명동 201동 서측 세대 실측에서 부하 0 간선
**1,114개 / 587m** 가 제거되었고, 최종 선정망은 79 pipe · 총연장 79,248.8mm 로
`load_mode=False` 와 완전히 동일했다(회귀 없음, 부착 헤드 손실 0).
①은 §4 표대로 아직 해결되지 않는다 — L1 부하 정의의 한계이며 `BLOCKED.md` §11 에 기록.

## 6. 담당 헤드 수의 이중 용도

누적값의 도메인 정체는 **담당 헤드 수**이고, 이는 그대로 **NFPC 103 별표1 '가'칸**
최소 호칭경의 입력이다. 즉 "추출 소속 판정"과 "법정 최소 호칭경"이 같은 양을 쓴다.
그래서 S430 의 별도 재귀 계산 경로를 없애고 `compute_edge_load` 로 단일화했다
(같은 트리·같은 헤드 집합에서 79 구간 전부 일치, 호칭경 불일치 0).
**헤드 집합만은 통합하지 않았다** — §4 마지막 행 참조.

## 7. audit 스키마

`ExtractionAudit` → 응답 JSON `extraction_audit`:

```
load             {min, max, median}          # 생존 간선의 부하 분포
pruned           {dead_edge_count, dead_len_mm, cycle_cut_count}
residual_cycles  {count, policy}             # policy: preserve | force_tree | off
unreachable_heads [[x, y], ...]              # 조용한 drop 금지
fallback         {triggered, reason}
```

## 8. 특허 정합 — `# [문서정합]`

현행 명세서 초안은 **"가지식 트리 강제(Dijkstra SPT)"** 를 청구 메커니즘으로 기재하고
있으나, 본 구현의 절단 기준은 **부하(담당 헤드 수) 0** 이다. 두 기준은 죽은 배관 처리에서
결과가 갈린다(§5). 명세서가 아직 미제출이므로 이 차이를 반영할 여지가 있다.

코드에는 `# [문서정합]` 주석만 남겼고 명세서 수정은 범위 밖이다. 목록:

- `remote30_prototype.py` `force_spanning_tree` — 명세서가 청구 메커니즘으로 기재한 SPT 강제.
- `remote30_prototype.py` `prune_by_load` — 실제 채택한 부하 기준 절단.
