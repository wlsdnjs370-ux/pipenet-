````markdown
  동일 (한 번만 고치면 됨)

같은 위치)에 순수 함수로 만들고 양 브랜치가 import 하게 한다.

## 이 저장소의 기존 원칙 — 위반하지 말 것

1. 모르는 값을 0 이나 기본값으로 조용히 때우지 않는다.
   ELEV_SOURCE_UNRESOLVED / ProjectContext.unconfirmed() 가 그 구현이다.
   새로 만드는 판정도 실패하면 조용히 continue 하지 말고 카운터나
   UNRESOLVED 로 노출한다.
2. 상수에는 그 값을 그렇게 정한 근거를 주석으로 남긴다
   (remote30_constants.py 의 기존 주석 스타일을 따를 것).
3. 골든 파일(tests/characterization/golden/)은 임의로 재생성하지 않는다.
   수치가 바뀌면 BLOCKED.md 에 §번호를 새로 붙여
   "항목 / 질문 / 임시 우회 / 실측 확인" 형식으로 기록하고 사람의
   육안 확인을 기다린다. 기존 §7 §8 §10 이 그 선례다.
4. NFTC 수치는 core/design/deterministic/nftc_tables.py 와
   constraints.py 밖에서 새로 쓰지 않는다.

## 자산 파일 주의

표준 SLF 는 사본이 여러 개 있고 내용이 서로 다르다.

  main/assets/2. Pipenet_hand_FX28.slf     FX 25A/내경 28
  domain-slim/2. Pipenet_hand.slf          FX 25A/내경 25
  samples/slf/OA_3-1형_..._35F.slf         구 샘플, 스케줄명·펌프가 다름

사내에 FX 20A/내경 21.6 인 사본도 존재한다. 코드가 실제로 해석하는
경로는 REMOTE30_STANDARD_SLF 환경변수 → 모듈 디렉토리 fallback 이다
(remote30_prototype.resolve_standard_slf).

**SLF 값을 근거로 무언가를 판단하기 전에 반드시 그 시점에 해석되는
파일을 직접 파싱해 확인할 것.** 이 문서에 적힌 수치는 2026-08-06
스냅샷 기준이며 현재 파일과 다를 수 있다.

- 진단이 틀렸으면 고치지 말고 무엇이 다른지 먼저 보고한다.
- 커밋은 작업 단위로 하나씩. 한 커밋에 여러 항목을 섞지 않는다.
````

## 1. CPVC2·3576 내경이 강관으로 대체되는 결함

> **성격** 실제 결함. 공유 파일이라 한 번만 고치면 양 브랜치에 반영된다.
> **선행** 없음. 가장 먼저 착수.

````markdown
# 작업 1 — 재질별 내경 조회가 CPVC/스테인리스에서 강관으로 폴백한다

## 증상

core/hb_rules.py 의 get_inner_diameter_mm() 에서:

    material_key = "3507" if "3507" in material else "3562" if "3562" in material else "3507"

"CPVC2" 나 "KSD 3576" 은 두 조건 모두 불일치 → else 가지로 떨어져
**강관(3507) 내경을 돌려준다.** 실행으로 확인했다:

    25A  3507: 27.5   CPVC2: 27.5   3576: 27.5
    65A  3507: 69.0   CPVC2: 69.0   3576: 69.0

## 실제 값 (권위 SLF 의 Schedule-section — 작업 전 직접 파싱해 확인할 것)

  CPVC2  (25~80A 만 존재)
    25A 28.02 / 32A 35.5 / 40A 40.63 / 50A 50.88 / 65A 64.0 / 80A 75.1
  KSD 3576
    15A 17.5 / 20A 23 / 25A 28.4 / 32A 37.1 / 40A 43 / 50A 54.9 /
    65A 70.3 / 80A 83.1 / 90A 95.6 / 100A 108.3 / 125A 133 /
    150A 158.4 / 200A 208.3 / 250A 259.4 / 300A 309.5

## 영향

core/hydraulic_solver.py 의 converge_bores_by_velocity 가 이 내경으로
유속을 재므로 CPVC 구간에서 유속을 과소평가한다.

    호칭   코드(강관)  실제 CPVC2   유속 과소   HW손실 과소
    25A      27.50       28.02       -3.7%       -8.7%
    32A      36.20       35.50        4.0%       10.0%
    40A      42.10       40.63        7.4%       18.9%
    50A      53.20       50.88        9.3%       24.3%
    65A      69.00       64.00       16.2%       44.2%
    80A      81.00       75.10       16.3%       44.5%

세대 진입 관경이 통상 65A 라 가장 자주 쓰이는 구간에서 비보수측으로
어긋난다. PIPENET 최종 계산은 SLF 의 올바른 내경을 쓰므로 계산서 자체는
맞다. 틀리는 것은 **관경을 정하는 판단**이다.

## 요구 동작

1. _KSD_INNER_DIAMETERS_MM 을 재질 열이 3507/3562/3576/CPVC2 인
   구조로 확장. CPVC2 는 25~80A 만 채우고 나머지 호칭경은 키 자체를
   두지 않는다 ("세대 내부에만 쓴다" 는 사실의 코드적 표현이다).
2. 재질 문자열 → 열 판정을 명시적 매핑으로 바꾼다. 매칭 실패 시
   **조용히 3507 로 떨어지지 말고 None 을 반환**한다.
3. None 이 올라온 자리(hydraulic_solver.inner_diameter_mm)에서
   호칭값을 그대로 쓰는 현재 폴백은 유지하되, 그 사건을 카운트해
   converge_bores_by_velocity 의 반환 리포트에
   `unresolved_inner_dia: {material: count}` 로 노출한다.
4. CPVC2 로 90A 이상을 요청하면 그 배관을 UNRESOLVED 로 잡는다.

## 검증

- 단위 테스트: 재질 4종 × 호칭경 전 범위 조회가 SLF 파싱 결과와 일치.
  SLF 를 파싱해 기대값을 만드는 테스트로 쓰면 라이브러리가 바뀔 때
  같이 깨져서 좋다.
- 대명동 201동으로 converge_bores_by_velocity 재측정. 기존 실측
  기준선은 changed=0 / 위반 0 / 과토출 1.27배 / 소스압 2.10 bar
  (BLOCKED.md §7). CPVC 구간이 있는 도면이면 changed 가 늘어날 수 있다.
- 골든이 흔들리면 BLOCKED.md 에 기록하고 재생성하지 말 것.
````

## 2. HSP 부스터 펌프가 존재하지 않는 라이브러리를 참조한다

> **성격** 실제 결함. 강의에서 지목된 "펌프 곡선 미입력 시 PIPENET 이 양정을 임의 선정" 문제의 코드적 실체.
> **선행** 없음. 작업 1과 병행 가능.

````markdown
# 작업 2 — Pump-fan 이 SLF 에 없는 Library-pump 를 가리켜도 아무 경고가 없다

## 증상

core/remote30_full_network.py:

  - ZoneSpec.pump_library_name 기본값이 "SP_162M_2900LPM" (3곳 하드코딩,
    주석에 "표준 SLF 와 정합" 이라고 적혀 있음).
  - 그런데 권위 SLF 의 Pump-section 에 그 이름이 없다. 내 스냅샷에서
    확인된 이름은 TEST1 / TEST11 / SP PUMP / OP_SP_PUMP_NEW 였고,
    사내 다른 사본에는 PUMP_156M_2800 / PUMP_73M_2800 이 있다.
    사본마다 다르므로 **작업 전에 실제 해석되는 파일을 파싱해
    목록을 확인할 것.**

  - _inject_pump_definitions() 가 없는 펌프를 NFPC 3점 곡선
    (체절 140% / 정격 / 150% 에서 65%) 으로 만들어 주입하도록 되어 있으나,
    주입 조건이 rated_q / rated_h 존재다:

        q = float(pump.get("rated_q", 0) or 0)
        h = float(pump.get("rated_h", 0) or 0)
        if q <= 0 or h <= 0:
            continue        # ← 조용히 건너뜀

  - rated_q / rated_h 를 싣는 곳은 prepend_machine_room_to_riser 뿐이고,
    HSP 부스터 경로인 build_riser_hsp_pump → _pump_fan() 은 안 싣는다.

        def _pump_fan(label, in_lbl, out_lbl, *, library_pump,
                      efficiency=100, status=1):
            return {"label":.., "in":.., "out":.., "efficiency":..,
                    "status":.., "library_pump": library_pump,
                    "percentage_open": 1}
            # rated_q / rated_h 없음

결과: HSP_PUMP zone 의 SDF 가 정의되지 않은 <Library-pump> 를 참조하고,
주입도 안 되고, 경고도 없다.

## 왜 중요한가

PIPENET 은 펌프 성능곡선이 정의되지 않으면 양정을 스스로 선정한다.
그러면 "실제로 살 수 있는 펌프인지" 와 무관한 계산서가 나오고,
출력물만 봐서는 그 사실을 알 수 없다. 사람이 놓치는 유형의 오류다.

## 요구 동작

1. ZoneSpec 에 pump_rated_q_lpm / pump_rated_h_m 필드 추가
   (from_form / from_dict 파서에도 반영). 기본값은 두지 말고 None.
2. _pump_fan() 이 rated_q / rated_h 를 그대로 실어 보낸다 →
   기존 _inject_pump_definitions 가 자동으로 곡선을 만든다.
3. _inject_pump_definitions 의 `continue` 를 없앤다. 주입에 실패한
   library_pump 이름을 수집해 호출자에게 돌려준다.
4. **SDF 방출 직전 게이트 신설**: 모든 <Pump-fan> 의 Library-pump 이름이
   실제 SLF Pump-section 에 존재하는지 대조. 없고 주입도 못 했으면
   ProjectContext.warning_lines() 에
   `[미확정] pump_library_name — 펌프 성능곡선 (SLF에 없음, 주입 실패)`
   로 올린다. 방출 자체를 막을지는 기존 unconfirmed 처리 관행을 따를 것.
5. 하드코딩된 "SP_162M_2900LPM" 3곳을 상수 하나로 모으고, 그 상수의
   주석에 "이 이름이 SLF 에 실재해야 한다" 를 명시.

## 검증

- SLF 를 파싱해 Pump-section 이름 집합을 만들고, HSP_PUMP zone 으로
  SDF 를 뽑았을 때 참조 이름이 그 집합에 있거나 주입되었는지 확인하는
  통합 테스트.
- rated_q/rated_h 를 안 넣은 경우 warning_lines() 에 항목이 뜨는지.
- 곡선 3점이 0 / 정격 / 정격×1.5 범위인지 (min-flow=0, max-flow=peak_q).

## 곁들여 할 것 (선택)

권위 SLF 에 TEST1 / TEST11 같은 시험용 이름이 남아 있다. SLF 위생
점검 스크립트를 하나 만들어 두면 좋다 — 스케줄 6종 존재 여부,
CPVC2 범위 25~80A, FX 내경이 선택한 프로파일과 일치하는지, 펌프 이름
규약, 노즐 K값. pipenet_validator 가 워드 계산서를 검증하듯 SLF 를
검증하는 짝이다.
````

## 3. 부속 판정 — 직류/분류티 구분 + 엘보 각도 구멍

> **성격** 강의에서 확인된 실무 관행의 반영. 자동/수동 대조에서 부속 수가 어긋나는 주요 원인으로 의심.
> **선행** 없음. 다만 브랜치 격차 때문에 공유 모듈 신설이 전제.

````markdown
# 작업 3 — 부속 계상 규칙을 공유 모듈로 빼고 두 결함을 고친다

## 근거 (현업 실무자 강의, 2026-08-05)

  - 티는 흐름 방향이 바뀌면 분류티, 직진하면 직류티다.
    **직류티는 수리계산 프로그램에 입력하지 않는다.**
    마찰손실 비는 대략 10:1 (구경에 따라 5:1).
  - PIPENET 이 제공하는 부속은 45°/90° 엘보, 롱레디우스 엘보,
    볼·버터플라이·게이트 밸브, 논리턴 밸브뿐이다. 그 밖의 것
    (스트레이너 등)은 커스텀 라이브러리로 만들어 KS 등가길이를 넣는다.

## 결함 A — 모든 티가 분류티로 나간다

remote30_prototype.py, build_input_tables 안 "====== Fittings ======" 블록:

    for p in tables.pipes:
        if node_degrees[p["in"]] >= 3:
            tables.fittings.append({..., "type": "tee", "count": "1"})

차수 3 이상 노드에서 나가는 **모든** 관로에 tee 를 단다. 그리고
core/has_converter.py 의 _FITTING_TO_CNT 에서 "tee" → "CntDivideTee",
calibration/compare_reports.py 의 FITTING_TYPE_NAMES[4] 는
"티/크로스(90° 전환)" — 즉 전부 분류티다.

교차배관 spine 을 직진으로 지나가는 관로는 원래 부속이 0 이어야 하는데
분기 개수만큼 분류티가 붙는다.

## 결함 B — 엘보 각도 구간에 구멍이 있다

같은 블록:

    if 43.5 <= angle_deg <= 46.5:  ftype = "elbow-45"
    elif angle_deg >= 70:          ftype = "elbow"
    else:                          continue      # 46.5~70도가 통째로 사라짐

46.5~70° 배관이 아무 손실 없이 지나간다.

## 요구 동작

1. **공유 모듈 신설** — fitting_rules.py (remote30_constants.py 와 같은
   위치, 양 브랜치가 import). 순수 함수만 두고 코드 의존을 만들지 않는다.
   입력은 노드 좌표와 그 노드에 물린 관로들, 출력은 부속 목록.

2. tee 판정: 노드로 들어오는 방향 벡터와 나가는 방향 벡터의 각도로
   가른다. 직진(임계 이내)이면 부속 없음, 꺾이면 "tee".
   임계는 remote30_prototype._classify_branch_edges 의
   TRUNK_TURN_TOL(45°) 과 **같은 상수를 공유**할 것 — 두 판정이 서로 다른
   자를 쓰면 "가지로는 분류됐는데 티는 안 달린" 조합이 생긴다.

3. 엘보 각도 구간을 빈틈없이 덮는다. 경계값은 코드에 근거 주석과 함께
   상수로 둘 것. 판정 불가로 버리는 경우는 조용히 continue 하지 말고
   카운터에 남겨 리포트에 "각도 판정 불가 n건" 으로 노출한다.

4. 부속 판정은 **직교화/평면화 이전 각도**로 해야 원본 도면과 맞는다.
   현재 호출 위치가 orthogonalize_edges / planarize_edges 뒤인지 확인하고,
   뒤라면 앞으로 옮기거나 원본 각도를 함께 들고 내려오게 한다.

5. 두 브랜치의 build_input_tables 가 이 모듈을 호출하도록 바꾼다.
   같은 로직을 양쪽에 복사하지 말 것.

## 하지 말 것

- 이번 작업에서 부속 등가길이를 내부 솔버 해석에 넣지 말 것.
  BLOCKED.md §7 질문2 가 "미모델링 + safety=1.1 로 상쇄" 로 기록한
  별도 과제다. 개수가 정확해진 뒤에 손댄다.
- 도면에 없는 부속을 만들어내지 말 것.

## 검증

- 합성 케이스 단위 테스트: 십자 교차(직진 1 + 분기 2), T 분기,
  일직선 관통, 45° 꺾임, 60° 꺾임 각각의 기대 부속 목록.
- 대명동 201동 / B1F 로 부속 개수 전후 비교. **줄어드는 것이 정상**이다.
- calibration/compare_reports.py 로 수작업본과 대조해 부속 개수·종류별
  분포·등가길이 합이 어느 방향으로 움직였는지 기록.
- 골든 흔들림은 BLOCKED.md 에 새 §로 기록.
````

## 4. 라이저 상수·레듀서 규칙의 외부화

> **성격** 동작 변경이 아니라 규약의 노출. 자동본이 수동본과 다를 때 그 이유를 말할 수 있게 하는 것이 목적.
> **선행** 4-2(표고 기준면 정의 확정)를 먼저 끝내야 4-3 을 할 수 있다.

````markdown
# 작업 4 — 프로젝트별 값이 코드에 박혀 있다

## 4-1. 라이저 치수 하드코딩

core/remote30_full_network.py 의 _riser_upper / _riser_prv_to_av:

    _pipe("r1", "1", "2", 150, 20.95, 0.0)   # 옥상 수평 20.95m
    _pipe("r3", "3", "4", 150, 14.93, 0.0)   # 14.93m
    _pipe("r5", "7", "8", 150, 0.5,  0.0)
    _pipe("r7", "5", "10", 125, 1.5, 1.0)    # T분기 → 알람밸브
    _node("5", elev_av - 1.0)                # T분기가 AV 보다 1m 아래

특정 프로젝트 실측값으로 보이는데 전 프로젝트에 그대로 나간다.

## 4-2. 표고 기준면 정의가 코드 어디에도 없다 — 이것부터

압력표의 head_drop_m 을 **층 바닥에서 재는지 알람밸브에서 재는지**가
코드에 적혀 있지 않다. 현업 관행은 다음과 같다:

  - 입상관 T분기점 = 그 층 바닥 + 600mm
  - T분기점 ~ 알람밸브 수평거리 = 0.6 ~ 1.0m
  - 알람밸브는 T분기점보다 위 (수격방지기 유무로 형상이 갈림:
    없으면 엘보 1개, 있으면 T분기 + 엘보 2개)
  - 최상층 층고는 단열재 때문에 일반층보다 약 250mm 높다
  - 수조 기준면: 수조 바닥 + 600 + 물높이 100 = 700mm, BOP 기준
  - 기준점(Z=0)은 수조의 물이 다 소진된 최저 수위 — 최악 조건
  - 옥탑~최상층 낙차는 건물 고유값이라 도면 규칙으로 못 구한다

현재 코드는 T 를 AV 보다 1m **아래**에 둔다. 관행과 부호가 반대일
가능성이 있으나, 기준면 정의가 없으니 지금은 판정할 수 없다.

**작업 순서를 지킬 것:**
  (a) 압력표 head_drop_m 의 기준면이 무엇인지 확정하고 FloorRow
      docstring 과 CSV/엑셀 파서 주석에 명시한다. 확정할 근거가 없으면
      코드를 고치지 말고 그 사실을 보고한다.
  (b) 확정된 뒤에 부호와 값을 맞춘다.

## 4-3. 요구 동작

1. ProjectContext 에 필드 추가 (기본값은 관행값, sources 로 출처 태깅):

     tee_branch_above_slab_m    # 입상관 T분기 높이 (기본 0.6)
     tee_to_alarm_valve_m       # T분기 ~ 알람밸브 (기본 1.0)
     water_hammer_arrester      # bool — 부속 형상이 갈림
     roof_to_top_floor_drop_m   # 옥탑 구간, 도면에서 안 읽히는 값
     top_floor_extra_height_m   # 최상층 단열재분 (기본 0.25)

   _CONTEXT_FIELD_LABELS 와 unconfirmed() 에도 등록해서, 사람이 확정하지
   않으면 리포트 최상단 경고에 뜨게 한다.

2. r1 / r3 의 옥상 수평 길이도 같은 방식으로 올린다. 프로젝트 고유값을
   기본값으로 두되 확정 전에는 [미확정] 로 표시.

3. remote30_constants.py 에 상수 추가:

     # 관경 전이(레듀서)는 T분기점에서 이 거리 안에 있으면 T분기점에
     # 귀속시킨다. 현업 관행 — 300mm 를 독립 노드로 살리면 관리 포인트만
     # 늘고 그 차이는 오차범위 안이라는 판단. 25/32 가 갈릴 때는 불리한
     # 작은 쪽을 택한다.
     REDUCER_SNAP_TO_TEE_MM = 300.0

   현재 코드는 규칙이 없어서 결과적으로 같은 동작을 한다. 상수를 두는
   목적은 동작 변경이 아니라 **자동본이 수동본과 다를 때 그 이유를
   말할 수 있게 하는 것**이다. 스냅이 적용된 지점 수를 카운트해
   방출 리포트에 낸다.
````

## 보류 항목 — 1~4 이후에 착수

### 5. 대조 리포트에 차이 원인 코드 붙이기

`calibration/compare_reports.py` 의 `ReportProfile` 은 수동/자동 값을 나란히 보여주지만
차이의 **원인**을 말하지 않는다. 축별 행마다 원인 코드를 달면 표가
"틀렸다/맞았다"에서 "이 차이는 이 규약 때문"으로 바뀐다.

```
GRANULARITY   Shift 연속작도로 수동이 노드를 통합 (관로 수 차이)
TEE_POLICY    직류티 미계상 vs 전량 분류티
REDUCER_SNAP  300mm 구간 처리
MATERIAL_ID   CPVC 내경 출처 차이
ELEV_DATUM    T분기/알람밸브 기준면 차이
ROOF_DROP     옥탑 구간 수동 입력값
```

**지금 하면 안 되는 이유** — 이 코드 목록 자체가 작업 1~4의 결과물이다.
지금 붙이면 `TEE_POLICY`, `MATERIAL_ID` 를 "아직 안 고친 상태"로 박아넣게 된다.

### 6. 추출 경로 유속 플래그

`remote30_prototype._pipe_diameter()` 는 별표1 최소 + 도면 텍스트 매칭만 쓰고
유속을 전혀 보지 않는다. `converge_bores_by_velocity` 는
`routes/r30_combined.py`(계통도 통합망 경로)에서만 호출된다.

추출 경로에도 유속 검사를 붙이되 **관경을 바꾸지 말고 플래그만** 남긴다 —
추출은 도면을 옮기는 일이지 설계하는 일이 아니다.

**작업 1이 선행되어야 한다.** 내경이 틀린 상태에서 유속을 재면 그 플래그가
CPVC 구간에서 거짓이 된다.

### 7. 층별 관경 전이 층 산출

강사가 남긴 숙제: "최상층은 25·25·32 로 되는데 3개 층만 내려오면 유속이
오버하니 25·32 로 가야 한다. **몇 층까지 25·25·32 로 갈 것인지 한번 해볼
필요는 있다.**"

`converge_bores_by_velocity` 를 층 축으로 돌려 전이 층을 산출하는 얇은
스크립트. 현업이 감으로 하던 판단을 코드가 수치로 답하는 사례이므로
시연·논문 소재로도 쓸 수 있다. 6번 다음.

### 8. 부속 기호를 부속 계상에 사용

`_find_fitting_symbols()` 는 배관 레이어의 ARC 를 찾아 `_split_crossing_tees` 의
**게이트로만** 쓴다. 강사가 실물 도면에서 "눈에는 엘보 4개지만 플랜지 기호가
있으니 T 로 읽어야 한다"고 한 판정이 부속 종류 결정에 반영되지 않는다.

기호 좌표를 부속 계상 단계로 넘겨 기호가 있는 노드는 각도 판정보다 기호를
우선하게 하고, 플랜지 기호(평행 짧은 선 2개)를 탐지 대상에 추가한다.
poc3 가 이미 하는 일이므로 새 연구가 아니라 이식이다. 작업 3 다음.

### 9. 부속 등가길이를 내부 솔버 해석에 반영

`BLOCKED.md §7 질문2` — `<Fittings>` 등가길이가 해석에 안 들어가고
`safety=1.1` 유량 할증으로 상쇄되고 있다. 손실 과소 → 과토출 과소 평가 =
비보수측. `kfp_fittings_library_v3.json` 에 NFPA 13(2025) 28.2.4.4.1 출처의
등가길이 테이블이 이미 있다(스트레이너·스모렌스키 체크밸브까지 사용자 추가됨).

**작업 3이 선행되어야 한다.** 부속 개수가 틀린 상태에서 등가길이를 물리면
오차가 곱해진다.

## 부록 — 이 작업들의 공통 성격

작업 1·2·3 은 전부 **"틀린 값을 조용히 쓰고 있다"** 는 한 가지 유형이다.
CPVC 를 강관으로, 없는 펌프를 있는 것처럼, 직류티를 분류티로. 셋 다
결과물은 정상적으로 나오고 아무 경고도 안 뜬다.

강의가 3시간 내내 말한 것이 이것이다 — 출력물은 언제나 그럴듯하게 나오고,
문제는 그걸 검증할 방법이 없다는 것.

이 저장소는 이미 그 철학을 상당히 잘 구현해 놓았다
(`ELEV_SOURCE_UNRESOLVED`, `ProjectContext.unconfirmed()`,
"모름을 0으로 대체하지 않는다"). 이번 수정의 절반은 새 기능이 아니라
**그 원칙이 아직 미치지 않은 세 군데를 같은 원칙으로 덮는 일**이다.

그래서 우선순위가 하나로 정리된다.
**먼저 조용히 틀리는 것을 시끄럽게 틀리게 만들고, 그다음에 고친다.**
